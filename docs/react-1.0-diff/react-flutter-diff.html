Reading rule: verdicts compare schema declaration order (React) with declaration order (Flutter), because Lang calls in the repo's own notes are positional in schema order (Tag(t.priority, null, "sm") = text/icon/size, Col("Sales", sales, "number") = label/data/type, Callout("success", "Saved", "Done.", $showSuccess) = variant/title/description/visible, `Form("edit", Buttons(...), [fields...])` = name/buttons/fields). Verdict codes: P = exact parity (same slots, order, requiredness, defaults); N = same slots and order, only the prop NAME differs (a positional program still works); G = gap (React props Flutter lacks, or a requiredness mismatch); S = shape difference (different prop structure, types, or semantics — a positional program does NOT port as written); O = same props, different ORDER; X = Flutter has a prop React lacks (listed separately). A row can carry several codes.

(f) Version-baseline correction — read first

"react-ui 1.0" is wrong. The "1.0" belongs to the language, not the component package:

PieceVersion
OpenUI Lang (spec, updated 2026-10-26)1.0
@openuidev/lang-core / @openuidev/react-lang1.0.1
@openuidev/react-ui (npm latest, jsDelivr, package README)0.18.1

The 0.18 README itself says "react-ui 0.18 renders OpenUI Lang 1.0". Any statement of the form "react-ui 1.0" should be corrected to "react-ui 0.18.1 rendering Lang 1.0".

**0.17.0 → 0.18.1 component delta: the count was right, the identifiers were wrong.** The registered 0.18.1 set is 86 names — coincidentally the same count as the carried-over 0.17 baseline — but 11 of the baseline's identifiers do not exist in source (see §a/§c). Whether those 11 are 0.18 renames or were already the 0.17 GenUI names cannot be established from this checkout (no 0.17 source in it); what IS established is that the earlier report's "0 missing" verdict falls, because it was measured against the wrong identifiers. What is established for 0.18 as runtime (not component) change: lone action form, custom functions (defineFunction) and custom actions (defineAction), library.extend (add / override / remove), stored-message format (]]>openui: markers), new error codes unknown-function and no-root, action() replacing `tagSchemaId(z.any(), "ActionExpression")`, React 19 + react-lang 1.x peer deps.

Library-membership note (not a missing component, but a parity gap)

React ships two libraries: openuiLibrary (root Stack, full suite except FollowUp/Section) and openuiChatLibrary (root Card, chat-optimized; excludes Stack and Modal, includes FollowUpBlock, FollowUpItem, SectionBlock, SectionItem). Flutter ships one merged library, openUIStandardLibrary(), containing all 95 names. So a Flutter program may combine Stack with FollowUpBlock in one tree, which neither React library accepts, and Flutter has no chat-Card variant (no sources prop) and no general-Card variant (no variant or flex props). No component is missing on membership grounds, but the library-membership boundary is not preserved.

Settled example-level gaps (D1–D5, now schema-confirmed)

  • D1 — Stack: confirmed. All five flex props are schema props

(optional); Flutter Stack has none. A React program using direction: "row" / wrap: true cannot be expressed in Flutter.

  • D2 — TabItem / Input: confirmed as built-in schemas, not

illustrations. TabItem is (value, trigger, content); Input is (name, placeholder?, type?, rules?, value?).

  • D3 — Col third positional: confirmed: type enum(string, number,

action). Flutter Col lacks it, and its second prop is named values where React's is data.

  • D4 — Tag: confirmed: (text, icon?, size?, variant?). Flutter's

second slot is a string icon name where React's is an Icon ref, and Flutter has no size/variant.

  • D5 — Form / FormControl (largest structural divergence):

confirmed: Form(name, buttons, fields), FormControl(label, input, hint) with a single field ref (and SwitchGroup excluded from the union). React Form programs are not portable to Flutter as written, and vice versa. Side note: the general-library group note calls Buttons "the third Form argument" while the chat-library note calls it "the second" with the matching example Form(name, buttons, fields) — the schema order agrees with the chat note; the general note is inconsistent with its own schema.

Props Flutter has that React lacks (X-list, from the table above)

  • All five card blocks: title (React blocks have no title prop).
  • MetricIndicatorInline / MetricIndicatorWithStrikethrough: label

(React has no label; value is a bare string).

  • ImageBlock: caption (React has alt instead).
  • All form fields and selection groups: bind (React fields are

name-keyed; there is no bind prop) — and label on Input/TextArea/ Select/DatePicker/Slider (React fields carry name, not label).

  • CheckBoxItem / SwitchItem: value (React items are name-keyed

with description/defaultChecked, no value prop).

  • SectionBlock: title (React has sections + isFoldable).
  • Slider: declared defaults min=0, max=100 (React requires min/max

with no defaults) — leniency, not a new prop, but a contract difference: a React program omitting min/max is invalid; a Flutter program omitting them renders 0–100.

  • TextContent: the variant value 'normal' is not a React size

value (React: small/default/large/small-heavy/large-heavy).

(e) Flutter-internal notes (NOT React gaps)

Carried over from flutter-inventory.md. These are findings about the Flutter port itself; none of them implies a React component is missing or a React prop is wrong.

  • F1 — CodeBlock.language declared but never read. The renderer reads

only code and renders plain monospace text. This is the deliberate post-revert state (syntax_highlight implemented then reverted by user decision; CodeBlock stays plain text until a new highlighting decision). A program passing a language gets it accepted and silently ignored. (New source context: React's language is REQUIRED and FIRST, so the Flutter declaration order and requiredness both differ too — see §d.)

  • F2 — Image.alt only partially used. Never used as an accessibility

label/semantics; its only use is as the error-placeholder text (stringOf('alt', '图片加载失败')) — shown only when the network image fails, and showing '图片加载失败' when alt is absent.

  • F3 — Composite-item src dead read. The five composite item types

share one renderer case reading props['src'] for a leading image, but only VisualItem declares src. For SnippetItem / OverviewItem / ContextItem / CompositeItem a program cannot supply src through the Lang mapper (a third positional is an excess-args error and is ignored), so the read is dead code for those four types. Harmless, but the shared case implies an API the defs do not offer.

  • F4 — 12 parent-read-only components (by design, not a bug). Col,

Series, Slice, ScatterSeries, Point, SelectItem, ChipItem, FollowUpItem, CheckBoxItem, RadioItem, SwitchItem, OptionCard have no dedicated renderer case; standalone they render SizedBox.shrink, and each is read by its parent component. No registered component is entirely unhandled (F5: none registered-but- unrendered; F6: no other renderer-read-but-undeclared props).

  • **F7 — Renderer-side fallbacks that differ in spirit from the declared

contract (notes, not errors).** Select/Chip/CheckBox/Radio/Switch/ OptionCard value falls back to the item's label when absent; Input/TextArea value is only the initial value (bound state wins); Slider value chain is form-state → value → min → 0.0; CalendarHeatmap entries with unparseable date or non-num value are silently skipped; Series non-numeric entries become 0, Slice value / Point x/y become 0 via numOf.

  • Declared defaults are rare. Only four props in the whole Flutter

library declare a default: TextContent.variant = 'normal', Callout/TextCallout.variant = 'info', Slider.min = 0, Slider.max = 100. Every other fallback is renderer-side leniency (stringOf → '', nodesOf → [], numOf → 0), not a declared default — so "required" in §d means the mapper rejects an omitted prop, not that the renderer throws. Contrast React, where .default(...) is common (card-block layout/responsive, Chips/OptionCards type and items, EntityList size, IconText variants, EditableTable name/columns/ data, Form fields).

Remaining caveats (what the checkout could NOT establish)

1. Icon.category: existence confirmed (description + renderer), exact Zod type not established — the schema file lives outside the sparse checkout. 2. Positional call shape for Text / BoldText: first schema key is a defaulted enum (variant) and no repo example shows a positional Text(...) call; their §d verdicts are by NAME, not by position. 3. Whether the 6 non-Condensed extras exist as non-GenUI UI primitives under packages/react-ui/src/components, and the full Icon schema — not checkable from the sparse checkout; not guessed here. 4. The 0.17.0 → 0.18.1 rename question (were the 11 long names already GenUI names in 0.17?) — needs the 0.17 source, not in this checkout. 5. react-lang's own arg-mapping rules (positional vs named) live outside genui-lib; the positional reading used here rests on the repo's own group-note examples, not on the react-lang source.

What would close the remaining gaps

1. Decide the 11 renames (alias vs rename) — the cheapest fix in this report, and the only one that changes unknown-component failures for existing React programs. An alias table (old short name → new long name) preserves Flutter programs while accepting React ones. 2. Decide the Form shape (D5) — the largest structural divergence; it determines whether Form programs are portable at all. Note the Flutter bind model vs React's name model is a second, deeper form-system divergence behind the same decision. 3. Reconcile the two libraries — either split Flutter's single library into general + chat variants or document the merged library as a deliberate deviation (including the missing chat-Card.sources). 4. Props alignment pass over §d's 75 gap/shape rows, in priority order: charts (labels vs categories; Pie/Radial/SingleStacked labels+values vs slices), card blocks (item-slot shapes), form fields (name vs label+bind), then the long tail of optional styling props (variant/size/direction/flex). 5. Residual source checks (small): full Icon schema from components/_shared/icons, react-lang arg mapping for Text / BoldText, 0.17 tag source for the rename question.
